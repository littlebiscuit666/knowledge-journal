## 二、架构决策（面试可讲）

1. **音频不放数据库**：MP3 本体进 TOS，DB 只存元数据；播放 302 到 1 小时签名 URL，TOS 原生支持 Range（实测 206）。
2. **私人曲库优先**：所有 SQL 带 `user_id`，权限模型简单安全。
3. **推荐不搞算法**：规则统计打底，等行为数据多了再上协同过滤。
4. **存储层可替换**：上传/下载/删除/列举封装在 `src/storage/tos.js` 单文件。
5. **LLM 用量控制**：LLM 只在新歌入库时调一次（生成 30 字摘要），查询时全部本地计算——成本与延迟与"每问一次调一次大模型"是两个量级。
6. **双表示检索体系**（本项目最有讲头的一条）：同一曲库两套索引——
   - **语义面**：BERT 向量（text2vec-base-chinese），管"安静的/适合夜晚的"这类描述性需求；
   - **旋律面**：符号音级差序列，管"3 2 3 5 5 3 2 3"这类音乐性需求。
   两套索引互补不可替代，对应业界"多路召回"里完全不同的两路。
7. **资源审计先行**：动手装任何东西前先盘本机已有资源。今天先错后正——先装了 325MB 的 transformers.js 栈，后发现本机 Python 早就有 sentence-transformers + text2vec 权重缓存，全部卸载改复用。这个教训值 325MB。

## 三、点歌台 v2：本地向量语义匹配

- **管线**：新歌入库 → LLM 生成 30 字摘要 → `title + artist + album + 摘要` 整体嵌入 768 维归一化向量 → 存 `songs.embedding`（JSON 列）。查询时同样嵌入，**点积即余弦**，全量暴力排序取 Top3（19 首 < 10k，暴力比任何向量库都快）。
- **Python 服务化**：`scripts/embed_server.py` 常驻 127.0.0.1:3310（stdlib HTTP），Node 启动时自动拉起、健康检查等待、退出时回收子进程；`HF_HUB_OFFLINE=1` 离线用缓存权重。
- **实测**："想听安静点的、适合夜晚的歌" → Twilight Canopy/月影未落/荒原钟鸣；"来点轻快的英文歌" → 完全不同的另一组。text2vec 余弦普遍落在 0.3~0.6 窄带，**绝对值无意义看相对排序**。
- **成本账**：曲库规模化后 LLM 摘要费一次性增长，查询侧永远零成本。

## 四、灵感匹配：简谱旋律检索（今日最大新增）

**需求**：用户随手打一串简谱数字（不是精确片段，是"灵感"），系统找出曲库里音程走向最像的片段，报歌名+时间段+共鸣度，点击跳到那一秒播放。

**管线**：
```
音频 → 双转录器并行 → 音符[[音高,起点,时长]] → 入库两列
简谱数字 → 大调半音 → 音级差序列 → 半全局编辑距离 → 双视图取优 → Top5
```

**三个关键算法决策**（都可以当面试题讲）：
1. **匹配音程而不是音高**：同一旋律移调后绝对音高全变、相邻半音差不变 → 存"相邻差"序列，天然移调不变。节奏同理存比例不存秒数。
2. **八度坍缩**：音程 mod 12 折叠到 ±6 的"音级差"。动机是实测发现 pyin 有八度抖动（62→50→38 跳整八度），折叠后八度错误自动抵消，还顺带让单八度简谱查询能对上跨八度旋律——12 半音等距域里相隔八度=同一音级，这是乐理常识救工程。
3. **半全局编辑距离**：查询是片段不是整曲 → DP 里歌的前后缀免费跳过、内部跳一音罚 1，一次 DP 同时得到最佳距离和片段起止位置（回溯定位），Levenshtein 的"替换/插入/删除"正好对应用户"记错一个音/多打/漏打"。

**验收**：从 HeisPirate 转录里抽真实旋律片段当查询 → 100% 共鸣度、定位误差 <0.5s 找回；"小星星"开头 1 1 5 5 6 6 5 在月影未落 52 秒处撞出 100% 共鸣（曲库里真藏着一段小星星，惊喜时刻）。

**tanyunxi 案例复盘（今天最曲折的调试故事）**：
- 现象：用户拿 32355323 匹配 tanyunxi 完全无结果。
- 第一层：它压根没被转录——网页上传的歌 TOS 里是 UUID 文件名，本地 Music 文件夹没源文件，全量转录时被跳过。修复：新增 `fetch-missing-audio.js` 按 storage_key 从 TOS 拉回本地。
- 第二层：补录后仍匹配不上。滑窗统计铁证：该音型全曲没有任何窗口比 dist=4 更近（对照组月影未落有 12 处 dist=1）；piano roll 显示 pyin 全程跟住的是低音声部（42-58），主旋律（65-78 稀疏高音）完全丢失。**单声部转录器在复杂混音里会盯错声部**——这是"音频→符号 MIDI"稀缺且困难的根源。
- 修复：上 basic-pitch（Spotify 多声部转录，ONNX 本地推理）。**轻量安装**：`pip install --no-deps basic-pitch mido pretty_midi mir_eval resampy`，走已有 onnxruntime，避开正常安装会拖带的几百 MB TensorFlow。
- 终局发现两转录器**互补**：basic-pitch 完美找回 HeisPirate、看见 tanyunxi 的旋律，但在月影未落上反而不如 pyin → 最终**双视图架构**：每首存两列旋律（melody_json=pyin / melody2_json=basic-pitch+skyline 最高声部），查询各试一遍取优，任何一首歌都不退化。
- 排名公平性三连修：同一音频两个歌名去重（luna=恋爱寸止挑战，转录逐字节相同实锤）、并列时按"直接命中音程数"排序、Top3 放宽到 Top5。tanyunxi 最终 71%（7 音程中 5 中）进榜第 4，定位 12-17 秒段。

**诚实边界**：7 个数字区分度天然不足（大量歌曲含相近走向），10 个数字以上区分度好；密集混音转录仍有噪声，看排名别迷信绝对百分比。

## 五、密码安全一课（bcrypt 原理，顺手学的）

- 库里 `$2b$10$` + 22 位盐 + 31 位哈希 = 60 字符；**单向不可逆**（模运算+截断信息有损，只能暴力枚举），系统自己也不知道原密码 → 忘记密码只能重置不能找回。
- 盐只在**设密码那一刻**随机一次，之后从存储串前 29 字符读回来复用 → "同盐同密码必同结果"的确定性验证（compare = 取旧盐重算再比对，不是解密）。
- cost=10 表示内部跑 2¹⁰=1024 轮，实测本机 48ms——**慢是特性**：MD5 一秒几亿次，bcrypt 一秒几十次，暴力破解成本抬百万倍；随机盐废掉彩虹表。
- Node 的 `bcrypt.hash/compare` 和 Python 的 `hashpw/checkpw` 同一标准算法，跨语言通用。

## 六、踩坑记录

1. **TOS Node/Python SDK 差异**：类名 `TosClient`、参数 `accessKeyId/accessKeySecret`、签名 URL 与 HTTP 方法绑定（GET 签的 URL 发 HEAD 403）。
2. **continuationToken 显式传 undefined 签名 403**：必须条件传参（代码有注释）。
3. **两首歌同时响**：遗留标签页 + 无跨页互斥 → BroadcastChannel。
4. **Windows 孤儿进程**：杀 npm 外壳不杀 node 子进程，旧代码占端口"假启动"；`taskkill //PID //F` 后重启。
5. **方舟 key 引号陷阱** + plan 端点只认部分模型别名（`claude-sonnet-4-5` 可用）。
6. **Windows curl 发中文变 GBK 乱码**：嵌入的是乱码导致排序错乱，一度误判算法有 bug；浏览器/node fetch 是 UTF-8 无此问题——**测试带中文的 API 务必用 node fetch**。
7. **pyin 音高是小数**（如 45.15）：与整数半音查询不同格子，每处对齐都被罚分 → 入库时量化 `Math.round`。
8. **pyin 八度抖动**：靠八度坍缩解决（见第四节）。
9. **Node 24 Windows 退出断言崩溃**：脚本 `process.exit()` 时还有未决 fetch 句柄会触发 libuv assertion → 退出前 `setTimeout 150ms` 缓冲（纯观感）。
10. **同一音频两个文件名**：luna 与 恋爱寸止挑战 转录逐字节相同才发现是重复入库，检索层已自动去重。
