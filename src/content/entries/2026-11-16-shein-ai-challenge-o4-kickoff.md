## 三、O4 赛题拆解（100 分）

作品三部分：**消费者玩法**（体验 30 分）+ **AI 一句话配置工具**（25 分，14 条评测需求：G01-G08 生成 / M01-M04 修改 / X01-X02 歧义拦截，脚本按槽位比对）+ **统一发奖接口压测**（工程质量 15 分）+ 运营可用性 8 项 20 分 + 创意表达 10 分。

硬性红线（易漏）：

- 每条 AI 输出附生成日志，输出文件 **SHA-256 须与日志一致**；人工改动必须标 `manual_edits` 否则违规
- 门槛 G1：评委**换随机种子**复跑 checker 须 exit 0；`--audit` 模式也要过
- 决赛会**现场用系统跑需求变体**复核——AI 配置必须是真系统
- **发奖服务必须在 AI 服务不可用时仍能运行**（ENG-04），LLM 只能出现在运营侧
- 评委机复跑 P95 ≤ 100ms 拿满 2 分；不实现 `/api/reset` 则 X2 项 0 分
- 作品不得出现真实品牌/真实商品图；AI 文案不许诺未抽中的奖品

## 四、官方基线并发缺陷修复（第 1 周任务提前完成）

官方给的 `baseline_server.py` 留了一个典型并发缺陷，跑 checker 复现失败：

- **A 零超发挂**：库存 108 实发 109；**C1 次数上限挂**：392/400 用户超次
- 根因：`handle_draw()` 的 **check-then-act（TOCTOU）竞态**——读 `used`/`issued` → 判断 → `sleep(0.5ms)` 拉宽窗口 → 才写回，全程无锁；ThreadingHTTPServer 每请求一线程，同一用户两个并发请求读到同一个旧值，双双通过检查
- 修复：`Activity` 加 `threading.Lock`，`handle_draw` 变薄包装把整个临界区锁住（原逻辑一行没动）
- 验证：**checker exit 0 全绿 + `--audit` 模式也 exit 0**

经验：锁内 sleep 使 P95 从 10.9ms → 72ms、吞吐 931/s——过门槛够用，正式服务要把临界区收紧（DB 写模拟移出锁外或改 sqlite 事务）。

## 五、消费者玩法 Demo（第一版可玩）

玩法：**穿搭盲盒 + 图鉴收集**。每天 3 次开盒 → 单品按稀有度（常规 62% / 稀有 28% / 传说 7% 限量 5 份 / 谢谢参与 3%）；8 件 City Look 单品收集，重复 ×3 → 奖励 1 次，集齐整套 → 限定礼盒。

单 HTML 文件实现，已验证四个状态：首页三秒看懂 / 开盒结果弹层 / 规则概率公示表 / 图鉴 8/8 集齐。设计考量：

- 回访理由 = 每日次数 + 收集进度；分享理由 = 图鉴与稀有度炫耀（评分里 CX-R 占 10 分，就看这个）
- 原创性稳：收集机制叠加 gacha，避开"抽奖赢好礼加个转盘"的官方反例
- 待替换：emoji 占位 → AI 生成插画（虚构商品）；内存态 → 服务端 sqlite + `/api/draw`

## 六、关键设计决策

- **单人 + AI 作战**：方案按 AI 承担主要实现收紧范围
- **LLM 用 DeepSeek**（便宜、JSON 输出强、国内访问稳、决赛现场演示风险低），仅用于运营侧配置工具
- **技术栈倾向 Python 纯标准库**（http.server + sqlite3 + urllib，零依赖 = 评委干净环境 2 次启动机会零失败面）+ 原生 JS 前端（无构建）
- 待做设计点：次数语义（`per_user_draws` = 每日次数，附加奖励在规则页说明）、进行中修改保留数据（配置版本化 + 计数延续）、版本回滚、跨站点复用
