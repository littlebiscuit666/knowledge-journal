## 一、这个项目在干什么

很多在役设备（进料泵这类机泵）**没有数字接口，PLC 拿不到直接的开关机信号**。本项目通过 IoT 采集的**振动、电流等属性数据**，用"测点对齐 → 数值插补 → AI 检测"的流计算链路，实时反推设备的**开机/关机动作**，输出结果供运行时长统计、启停次数、能耗分摊、设备利用率（OEE）分析使用。

**平台形态**：DEP 平台的可视化流计算画布（算子编排式开发），作业名"进料泵设备开关机检测"。画布上的链路：

```
IoT属性数据 → 测点对齐 → 数值插补 → 开关机检测 → 流表输出
```

平台算子清单（左侧面板）：输入（IoT属性数据 / IoT规则引擎）、基础处理（过滤 / 数据计算）、计算算子（测点对齐 / 连续超限 / 数值插补 / 极差超限 / 开关机检测）、输出（IoT属性输出 / 流表输出 / IoT事件中心）。

> 特征统计量（标准差）、模型输入输出都在算子上配置完成，底层生成对应的窗口聚合与推理逻辑——算子化配置代替手写 SQL，这是平台的核心开发方式。

## 二、五个环节详解

### 1. IoT 属性数据（输入）

边缘侧采集的属性数据经 MQTT 等协议上报进平台。本作业的输入特征（5 个测点，统计量均为**标准差**）：

| 字段 | 复原含义 | 作用 |
|---|---|---|
| `mtrde_3v_vibr` | **电机驱动端**（Motor Drive End）3号测点 振动标准差 | 运行时振动波动有稳定特征，停机时接近噪声底 |
| `mtrde_3a_vibr` | 电机驱动端 3号测点 另一方向振动标准差（v/a 待核实：垂直/轴向 或 速度/加速度） | 多方向互补，防单点误判 |
| `pmpde_2v_vibr` | **泵驱动端**（Pump Drive End）2号测点 振动标准差 | 区分"电机转但泵没带负荷"等工况 |
| `pmpde_2a_vibr` | 泵驱动端 2号测点 另一方向振动标准差 | 同上 |
| `current` | 电机电流标准差 | 最强特征：启动瞬间电流冲击（6~8 倍额定），停机归零 |

### 2. 测点对齐

**一句话：把同一设备上、上报节奏各不相同的多个测点，整理到统一时间轴上，让"同一时刻的多个指标"真正可比。**

为什么必须做：
- 各测点**采集频率不一样**（电流 30s 一次、振动 1min 一次），原始数据里没有一行是五个值都齐的；
- 各传感器/网关**时钟有偏差**；
- 存在**缺口**（丢包、断连）。

落地实现（底层 ClickHouse SQL）：

```sql
toStartOfFiveMinutes(data_time) AS window_t   -- 5分钟时间栅格 = 对齐基准
```

- 固定 5 分钟栅格，各测点按时间戳归入所属窗口，窗口内做聚合；
- 同时做**语义对齐**：原始点位 → 设备/部位/单位的映射（关联测点元数据）；
- 对齐后形成"一行 = 一个设备一个窗口的全部特征"的宽表。

> 概念辨析：**对齐是目的，时间窗口是手段之一**。窗口在这里一箭双雕（聚合口径 + 对齐栅格）；实时低延迟场景也可用就近匹配（Flink interval join / ASOF JOIN）代替窗口栅格。

### 3. 数值插补

模型吃的是**连续窗口序列**，缺一格格子特征序列就断。排在插补对齐之后：

- **补栅格**：生成设备完整的 5 分钟窗口序列，与特征表 LEFT JOIN 让缺口显形；
- **短缺口（1~2 窗）**：前值延续（LOCF）或线性插值；
- **长缺口**：不硬补，保留空并打质量标记；
- **铁律：插补值必须带标记**（imputed_flag / 缺失率）——可参与判定，不得当真实数据进统计。

### 4. 开关机检测（结合 AI 组的能力）

**三分类事件检测模型**：输入对齐+插补后的连续特征序列，输出该窗口发生「开机动作 / 关机动作 / 无动作」的概率——判的是**状态切换动作**，不是状态位。

模型输出参数（算子配置页确认）：

| 属性名称 | 字段 | 类型 |
|---|---|---|
| 设备唯一标识 | `device_id` | STRING |
| 动作类型 | `action` | STRING |
| 最高概率值（置信度） | `confidence` | FLOAT |
| 无动作概率 | `prob_no_action` | FLOAT |
| 开机动作概率 | `prob_start` | FLOAT |
| 关机动作概率 | `prob_stop` | FLOAT |
| 预测时间 | `time` | TIMESTAMP |
| 是否支持预热 | `warmup_available` | BOOLEAN |

业务规则：
- `action = argmax(三个概率)`，`confidence` 即最大概率值；
- 下游设**置信度阈值**（如 ≥0.7 才算有效动作），防低置信度乱发事件；
- `warmup_available`：机泵启动后有过渡工况（电流冲击、振动骤增），该字段与预热期处理逻辑有关（语义以 AI 组接口文档为准，待核实）。

### 5. 流表输出

检测结果**持续写入一张结果表**（动态表），一次写入、流批共用：下游不关心计算过程，直接查最新状态与历史动作记录；离线任务也可读同一张表做回刷统计——这就是"流批一体"。

## 三、底层 SQL 复原（ClickHouse）

画布算子底层生成的逻辑大致如下（我从平台脚本里复原的片段 + 顺推）：

```sql
-- 步骤2：直接取出原始指标值（特征已由上报侧算好，不做转换）
SELECT
    product_key,
    device_key,
    toStartOfFiveMinutes(data_time) AS window_t,   -- 测点对齐：5分钟栅格
    mtrde_3v_vibr, mtrde_3a_vibr,                   -- 以下均为窗口标准差特征
    pmpde_2v_vibr, pmpde_2a_vibr,
    current
FROM ${sinopec}.ods_sinopec_device_rawdata          -- ODS 层原始表
WHERE product_key = {{product_key}}                 -- 调度参数：按设备循环实例
  AND device_key  = {{device_key}}
ORDER BY data_time
```

后续步骤顺推：窗口聚合（如 ODS 为明细则按 window_t 聚合）→ 插补补栅格 → 调 AI 模型推理 → 写流表。

三个藏在 SQL 里的数据开发细节：
- `toStartOfFiveMinutes()` = 测点对齐的栅格实现；
- `{{product_key}}`/`{{device_key}}` = 平台调度参数，**按设备参数化循环**，单设备失败不影响其他设备；
- `${sinopec.ods_xxx}` = 跨项目空间引用 ODS 表，原始层不加工（数仓分层规范）。

## 四、数据开发细节清单

- **分层**：ODS（原始上报）→ DWD（对齐+插补后的特征宽表，含质量位）→ ADS/流表（检测结果）→ 事件配对（运行时长/启停次数）→ 应用；
- **幂等重跑**：结果表按 `device_id + window_t`（或 `data_date` 分区）幂等，重跑分区替换，避免重复事件；
- **断流监控**：设备最新 window_t 落后当前时间超过 N 个窗口 → 告警（传感器掉线，插补救不了，需人工介入）；
- **插补率统计**：按设备统计插补占比，突增 = 采集侧异常信号；
- **事件配对**：start/stop 交替配对、同向动作去重，`运行时长 = stop − start`，产出启停次数与运行时长；
- **流批一体**：实时链路保时效，离线脚本（上面的 CH SQL）负责回刷补算，口径以 5 分钟窗口栅格为准；
- **平台旁路能力**：画布还有「连续超限」「极差超限」等规则算子（阈值类告警）和「IoT事件中心」输出——本作业用的是 AI 算子 + 流表输出的组合，规则算子适合简单阈值场景，AI 算子适合工况复杂的启停判定。

## 六、常见追问 Q&A

**Q1：测点对齐到底对齐什么？**
时间对齐（不同频率→统一 5 分钟栅格）+ 语义对齐（点位→设备/部位/单位的元数据映射）。

**Q2：为什么不直接阈值判定，要绕插补和对齐？**
多信号判定要求同一时刻的值可比；缺口不补会被模型当成"关机"误判。AI 模型替代纯阈值是因为机泵工况复杂（变频、负载变化），固定阈值误报率高。

**Q3：插补怎么做的？**
短缺口 LOCF/线性插值，长缺口不补只标记；所有插补值带质量位，可参与判定不进统计。

**Q4："流表"是什么？**
流计算结果持续写入的动态表：一次写入、流批共用，下游 API/报表直接查，无需感知计算过程。

**Q5：窗口为什么选 5 分钟？**
粒度由判定精度与模型输入共同决定：够平滑瞬时抖动（标准差即在此窗口上算），又不至于漏掉短暂启停。
